# PIDL v0.9.0 Release Notes

**Release Date:** Unreleased

This release takes the walkthrough beyond one HTML file. The walkthrough is now a documented format that any page can show with one script tag from a CDN. Each request can be read as HTTP, as a `curl` command or as SDK code from tested source files. Steps can be narrated in several languages for audio and video. And the same examples now drive a runnable Postman collection.

## Highlights

- **Embeddable viewer**: `@grokify/pidl-viewer` shows any walkthrough from a CDN with one script tag
- **Walkthrough format**: `pidl-walkthrough/v1`, with a JSON Schema and TypeScript types
- **Code samples and cURL**: each request as HTTP, a generated `curl` command, or SDK code kept current by a lock file; the AAuth example shows Go code from aauth-go
- **Postman collections**: a runnable collection per protocol, with values chained between requests and checks on every response
- **Narration**: spoken text by language, scenario briefings and pronunciations

## What's New

### Embeddable Viewer

```html
<div id="walkthrough"></div>
<script src="https://cdn.jsdelivr.net/npm/@grokify/pidl-viewer@0.9.0/dist-lib/pidl-viewer.js"
        data-pidl-target="#walkthrough"
        data-pidl-src="aauth.walkthrough.json"></script>
```

The script shows a walkthrough from inline JSON (`data-pidl-data`), a URL (`data-pidl-src`) or the page's `?src=` parameter, so one page can show any walkthrough. `PidlViewer.mount(element, {src | data})` does the same from JavaScript.

- The viewer renders inside a shadow root: the page's styles do not change it, and its styles do not leak into the page.
- Several viewers can share a page. Each takes the step keys only while it has focus.
- `?src=` loads only `https:` URLs or the page's own origin, and fetches without cookies.

`pidl generate -f viewer` still writes one self-contained HTML file for offline use. See [Embedding the Viewer](../guide/embedding.md).

### Walkthrough Format

`pidl generate -f walkthrough-json` writes `pidl-walkthrough/v1`, the processed form viewers read: every scenario with fragments expanded, each step's example, generated `curl` command, samples and narration, and analyzer findings. The format is now documented and versioned:

- `schema/walkthrough.schema.json` is generated from the Go types and embedded as `schema.WalkthroughSchemaJSON`, with a test that it is current and that every built-in example validates.
- The viewer's TypeScript types are generated from the schema, and ship in the npm package.
- A reader accepts any `v1` walkthrough, including one with fields it does not know, and refuses another major version.

See the [walkthrough format reference](../reference/walkthrough-format.md).

### Code Samples and cURL

Every example request now has an equivalent `curl` command. A signed request's command replays the example's signature headers and says so.

Steps can also carry code samples. A sample's code can come from a region between `pidl:begin` and `pidl:end` markers in a tested file of a repository, at a tag or commit:

```bash
pidl samples resolve aauth.json   # write the code and its hash to aauth.samples.json
pidl samples check aauth.json     # fail when a sample has fallen behind its source
```

Generation reads the lock file, so it never needs the source repositories or the network. In the viewer, each request and response has a tab for HTTP, cURL and every sample language. A step where nothing goes over HTTP, such as a person approving in a browser, can carry samples alone.

The AAuth example shows Go code from aauth-go's tested walkthrough for the agent, agent provider, resource, person server and access server. See [Code Samples and cURL](../guide/samples.md).

### Postman Collections

```bash
pidl generate -f postman --signer aauth-sandbox -o aauth.postman_collection.json aauth_protocol
```

A folder for each scenario holds a request for each step the client role sends. Values a response delivers, including string parameters of headers such as the resource token in `AAuth-Requirement`, are passed to the requests that reuse them. Each response is checked against its example, and deferred responses are polled.

- `--signer aauth-sandbox` sends signed requests through the AAuth sandbox's signing helper.
- `--mock` saves the example responses for a Postman mock server.
- `-f postman-environment` writes an environment for a named target.

See [Postman Collections](../guide/postman.md).

### Narration

Scenarios and steps can carry narration keyed by BCP 47 language, with the protocol's source language as the fallback. Scenarios can carry a briefing, steps can override their narration for the HTTP, cURL or code view, and pronunciations tell text-to-speech tools how to say terms. The walkthrough carries all of it for audio and video tools; the viewer does not play narration yet. See [Narration](../guide/narration.md).

### Scenario Structure

- **Groups** order scenarios into sections.
- **Variants** pair alternative forms of one journey and follow their base.
- **Step IDs** name steps, as `<include>.<id>` inside fragments, so links such as `#ps-authorization/consent.approve` keep working when steps are added.

### Petstore Example

`aauth_petstore` extends the AAuth example with the Petstore as an AAuth resource: browsing pets with the agent's identity, and ordering a pet with a person token and then an auth token for `write:orders` that the person approves.

### Library

- `ResolveOptions.FS` resolves the documents that `extends` and `imports` name from an `fs.FS`.
- Built-in examples apply their sample lock and resolve their `extends` when loaded.

## Fixes

- Sample source paths are checked the same way on every platform. The check used `filepath.IsAbs`, which does not treat `/etc/passwd` as absolute on Windows, so a test failed there. pidl now uses `ValidateSlashPath` from [oscompat](https://github.com/grokify/oscompat) v0.8.0, its first dependency, which depends only on the standard library.
